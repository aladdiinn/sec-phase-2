#21 — INVESTIGATION & FORENSICS
GRAPH-BASED RELATIONSHIP VIEW
A visual node-graph that maps every entity involved in an attack: Users → Hosts → IPs → Alerts. Instead of reading a list of events, analysts see the attack as a connected web — instantly understanding who connected where, when, and what it triggered.
HOW IT WORKS
Build with D3.js force-directed graph. Nodes = entities (IP, Host, User, Alert). Edges = relationships (logged-into, triggered, connected-to). Colour: red = malicious, orange = isolated, cyan = normal. Clicking a node shows its event list in a side panel.
WHERE TO PUT IT
Inside the Case Investigation view (when analyst clicks "Investigate Case #34"). Add a tab toggle: [Events List] [Relationship Graph]. The graph auto-builds from the case's event data — no manual input needed.
REAL EXAMPLE
Case #34 graph shows: IP 198.51.100.42 → (6 failed logins) → e2e-test-server → (triggered) → brute-force alert → (fired) → Auto-Isolate playbook → HOST ISOLATED. One visual, full attack story.

#24 — RESPONSE & CONTAINMENT
ACCOUNT DISABLE / PASSWORD RESET
When a user account is identified as compromised, analysts can disable the account or force a password reset directly from the SecurePulse incident view — without logging into Active Directory, Okta, or any other identity provider separately.
HOW IT WORKS
1
Analyst opens Incident/Case detail. Sees "Affected User: jake@company.com" identified in events.
2
Clicks "Disable Account" button in Actions panel. SecurePulse calls your AD/LDAP/Okta API to disable the user.
3
Confirmation banner: "Account jake@company.com disabled at 02:15AM by analyst A". Logged in Audit Trail.
4
"Force Password Reset" similarly calls the identity provider's reset API. User gets a reset email on next login attempt.
WHERE TO PUT IT
1. Incident/Case detail → right sidebar "Response Actions" panel

2. Also add as a Playbook action step so it can be automated

3. Settings → Integrations → "Identity Provider" config section (where you enter Okta/AD credentials)
ALSO ADD AS PLAYBOOK ACTION
In Playbook Builder, add action type: "disable_account" with parameter: "affected_user_from_event". Allows fully automated response: detect compromise → isolate host AND disable user simultaneously.

#33 — PLATFORM & INTEGRATION
HIGH AVAILABILITY & DISASTER RECOVERY
SecurePulse itself must never go down. HA means multiple instances run simultaneously — if one crashes, others continue without interruption. DR defines how fast you recover (RTO) and how much data you can afford to lose (RPO).
KEY CONCEPTS EXPLAINED
RPO (Recovery Point Objective) = max data loss acceptable. RPO of 1 min = you can lose max 1 minute of events if a disaster happens. Achieved by: database replication every minute.

RTO (Recovery Time Objective) = max downtime acceptable. RTO of 30 sec = service must be back within 30 seconds of failure. Achieved by: load balancer + standby replica auto-promotion.
SYSTEM HEALTH PAGE (UI to BUILD)
New page: Settings → System Health:
• Uptime counter (live, since last restart)
• Active replicas: list of nodes with status [PRIMARY] [REPLICA-1] [REPLICA-2]
• Replication lag: current ms lag
• Last DR test: date + result (PASS/FAIL)
• "Run DR Test" button (Superuser only)
• Alert if replication lag > threshold
// FEATURE #33 — HIGH AVAILABILITY & DR
INFRASTRUCTURE (DevOps layer):
• Deploy minimum 2 app instances behind load balancer (nginx/AWS ALB)
• Database: PostgreSQL primary + 1 streaming replica (or managed: AWS RDS Multi-AZ)
• Redis: Sentinel or Cluster mode for session/cache HA
• Target RPO: ≤ 1 minute (sync replication or near-sync)
• Target RTO: ≤ 30 seconds (auto-failover via load balancer health checks)

SYSTEM HEALTH PAGE (Settings → System Health):
• Page title: "SYSTEM HEALTH" — Orbitron font, same cyber style
• Uptime widget: live counter in HH:MM:SS (Orbitron, cyan)
• Nodes table: [Node Name] [Region] [Role] [Status] [Last Heartbeat] [CPU%] [Mem%]
• DB Replication section: Primary node, replica nodes, replication lag in ms
• "RUN DR FAILOVER TEST" button — Superuser only — sends test traffic to replica
• DR test history log: last 5 tests with timestamp + result
• Alert banner if: replication lag > 5s, any node down, health check failing

THE FLOW
1
CRITICAL incident created in SecurePulse → Jira issue auto-created (SEC-2847) → stored with incident
2
Incident detail shows: "Jira: SEC-2847 [Open]" with clickable link to Jira
3
Analyst resolves SEC-2847 in Jira → Jira webhook fires → SecurePulse auto-closes the incident
4
Status changes sync both ways: SP "In Progress" → Jira "In Progress" and vice versa
